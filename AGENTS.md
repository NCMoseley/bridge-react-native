## Data Normalization

- `bracketId`, `tradeId`, `eventId`, and `armId` values are normalized before storage or lookup: `value.replace(/[\r\n]/g, '').replace(/'/g, 'r')`.
- Carriage returns (`\r`) and line feeds (`\n`) are stripped; single quotes (`'`) are replaced with `r`.
- This protects the SQL identifier store and guarantees that `bracket-a\r` and `bracket-a` are treated as the same bracket.
- Always use the normalized value when doing bracket/lookup operations, not the raw incoming payload string.

## Range-Scoped Bracket Ids

- `scopePayloadIdsToRange()` (`src/webhook.ts`) prefixes a range token onto `bracketId`/`tradeId`/`eventId`/`armId`. It runs once inside `processProxyPayload` — every ingest caller (`/proxy`, lifecycle test sends, simulators) normalizes there — keyed on the *stored* range spelling (`resolveTrackedRangeName`/`resolveRangeName`) so the slug lands on the stored identity. Scoping the same payload under two different resolutions would double-prefix; keep it single-sited.
- `pinescript/ultra-v5.4.pine` `rangeSlug()` mints the same token natively (`ultra-v5.4-<slug>-<ticker>-<epoch>-<seq>`); `idCarriesRange` detects that native position only for v5.3+ ids and validates it structurally — the segment after the slug must be a ticker (contains a non-digit) followed by a numeric epoch. A pre-slug v5.3 id on a range named like its ticker still gets prefixed, and a claimed `<slug>-` prefix whose remainder starts with `-` belongs to a longer range's slug (prefix chains like 'SIM' vs 'SIM-ALL-MNQ'), not this one — both are re-prefixed rather than claimed. `ultra-v5.3.pine` is the deployed version — deploy 5.4 in TradingView, not a modified 5.3.
- Encoding is injective and case-preserving: `-` → `--`, cp ≤0xFF → `-XX`, cp >0xFF → `-uXXXX`, applied after `normalizeRangeName`-equivalent control-strip/whitespace-collapse.
- **Legacy transition**: `Database.resolveBracketMonitorId` maps a normalized incoming id back to an open (armed/filled) unprefixed monitor row when no normalized row exists — in-flight pre-deploy brackets keep their identity until they close. `unscopeEventIdsForLegacyBracket` stores the event under the legacy `trade_id`/`event_id` so journal identity doesn't split, but only when no exact scoped monitor row exists — an established scoped bracket never folds into a lingering legacy row sharing the base. Id-equality lookups (`trade_id`/`bracket_id`/`source_reference`) accept both forms via `idFormsForLookup` IN-clauses; row-returning lookups order the caller's exact form first (`ORDER BY (col = ?) DESC`) so a legacy row can never shadow the scoped row.
- **CrossTrade wire ids**: the ledger `order_id` carries suffixes the wire never sees — `-r<n>` (retry attempt) — while re-armed resends go out as `bracketId-a<n>` (NT8 burns used order ids). `matchesCtOrderId` / `ctWireOrderId` (`src/crosstrade.ts`) strip ledger suffixes and accept resend forms on the exact-id and `oco_id`+action match paths; `findCtEntryRow` picks the *newest* matching NT8 row so re-arm cycles attribute the right entry. A sweep retry re-pairs OCO: it cancels the still-working sibling arm (instrument-scoped `cancelorders`) and resends it under the same `-a<n>` group — skipped with a `crossTradeOcoUnpaired` warning when another bracket shares the instrument. Entry auto-retry re-sends the stored payload on `-a<n>` wire ids and runs BEFORE leg sync (a rejected arm looks identical to an orphaned arm). ct-flat synth `event_id` is trade-scoped (`ct-flat-<tradeId>-<side>-trade_closed`) so re-armed brackets journal a second close instead of conflicting on the first cycle's id.
- **Broker fill reconciliation**: `applyBrokerFillPriceToEntry` writes NT8 `averageFillPrice` into `bracket_monitor` + `trade_events`; ct-flat close synthesis uses it and applies before monitor retirement. Consensus exit fallback requires `ownerStrategy` matching the range.
- **Cache invalidation**: `invalidateUserCache` debounces SSE emits (≤1/400ms/user, trailing, cleared on close); `updateBrokerOrderStatus` invalidates after the write.

## Open Positions and Journal

- `bracket_monitor` is the authoritative source for whether a bracket is currently `armed` or `filled` from Pine/Ultra's perspective. The Open Orders list, EOD flatten, news flatten, reconcile, and reapply guards should all derive the set of open positions from `bracket_monitor` first.
- `trade_events` and `range_trade_events` are the Pine/Ultra lifecycle journal. They contain `entry_armed`, `entry_filled`, `entry_cancelled`, and `trade_closed` only from Pine lifecycle alerts. No synthetic `bridge-reapply` lifecycle rows.
- Ultra/Pine lifecycle ids (`event_id`, `trade_id`, `bracket_id`) are NOT range-unique — they are minted as `ultra-<ver>-<ticker>-<epoch>-<seq>-<side>-arm-<seq>` with no range component, so two ranges sharing an instrument and anchor epoch emit identical ids. Every lookup or dedupe key must include `range_name`: `trade_events` is `UNIQUE(event_id, account_id, range_name)`, `range_trade_events` is `UNIQUE(event_id, range_name)`, and `updateOpenEntryBrokerOrderStatus` / `hasAttemptedEntryOrder` / the adjustment-delete paths all scope by range. `reapply_operations.event_id` is stored as `<rangeName>|<eventId>`. Never add a bare `event_id`/`bracket_id` match without `range_name`.
- `broker_orders` is the source of truth for broker-side dispatch state. One row exists per TradersPost order attempt (`buy`/`sell`/`cancel`/`exit`) with a status such as `pending`, `acknowledged`, `rejected`, `uncertain`, `filled`, or `closed`. A dispatch is `acknowledged` only on a 2xx whose body explicitly reports `success:true`. `uncertain` means the request may have reached TradersPost (timeout, connection loss, 5xx, interrupted in-flight delivery, or a 2xx without `success:true`); only `success:false` bodies and definite 4xx rejections map to `rejected`.
- `broker_orders.status` is the row's effective state; `status_source` records who last wrote it (`dispatch` webhook response, `lifecycle` Pine event, `bridge` local bookkeeping such as reapply/EOD/safeguard retirement, `operator` reconcile UI, `email` failure-notification path, `legacy` pre-migration rows). `dispatch_status` preserves the last dispatch-observed outcome when a non-dispatch writer later overwrites `status`, so a Pine `entry_filled` can mark an order `filled` while `dispatch_status` still shows the send was only ever `uncertain`. The Monitoring broker-orders card renders both.
- `bracket_reapply_aliases` maps a Pine `bracket_id` to the current active `broker_orders` row. Open Orders are enriched with the active `broker_orders` delivery status so a `filled` `bracket_monitor` row with a failed delivery is visible.
- `bracket_monitor` enforces valid lifecycle transitions: `closed` rows ignore all later events, `cancelled` rows only accept `entry_filled`, and `filled` rows ignore `entry_armed` and `entry_cancelled` (a live position cannot be re-armed or cancelled; only a working order can). The journal still records such alerts faithfully — only the monitor state is protected. Force-close paths (`retireBracketMonitorEntry` via EOD/reconcile/safeguard) may override state deliberately.
- EOD, news-flatten, reconcile, and admin cleanup are the only sources of synthetic `trade_events`. They write `entry_cancelled` and `trade_closed` with `exclusionReason: 'erroneous'` only when forcibly closing an unfilled bracket that Pine never closed.

## EOD as Source of Truth

- The end-of-day (EOD) scheduler closes every open `bracket_monitor` row at the configured time, not just accounts with an enabled TradersPost destination. For accounts that have an enabled TradersPost destination with `eodEnabled` on, it also sends the `cancel`/`exit` payloads. If the TradersPost call fails for the configured retry window, the bridge still records the local `entry_cancelled` or `exit_filled`/`trade_closed` and retires the `bracket_monitor` row so the day is flat.
- An `armed` (unfilled) bracket that receives an EOD `cancel` 200 is recorded as `entry_cancelled` and as a `trade_closed` with `outcome: 'breakeven'`, then excluded from performance with `exclusionReason: 'erroneous'`. It appears in the Closed Trades section but does not affect P/L.
- A `filled` position that receives an EOD `exit` 200 is recorded as `exit_filled` and a `trade_closed` with `outcome: 'breakeven'`. It appears in the Closed Trades section and contributes $0 to P/L.
- In addition to open-state cleanup, the EOD scheduler sends instrument-scoped `cancel` and `exit` payloads for every recently-active instrument root on the account (last 24h of TradersPost entry deliveries plus currently open instruments), even when nothing is open locally. This clears stray broker-side orders/positions outside Bridge bookkeeping. These blanket sends require an enabled destination with `eodEnabled` on, skip crypto-future roots, dedupe against instruments already covered by the open-order/open-position paths, and share the same 5-minute retry window.
- News-flatten (red-folder) follows the same model: per-event per-account, retried each minute within the flatten window (up to `MAX_EOD_RETRY_MINUTES`); a pass is only marked done when every send delivers. Accounts whose destination is disabled — and deprecated accounts — record the local close without sending. Deprecating an account first closes everything out: a live destination gets the full `runCancelAllSafeguard` flatten over all submitted-state roots, then any remaining open brackets/positions are closed locally (`deprecated_close`/`deprecated` reasons) so the journal is flat before the account is marked deprecated.
- Deprecation disables rather than deletes: `range_routes` are switched off (`traderspost_enabled`/`extension_enabled` = 0) and the TradersPost destination is disabled, preserving delivery history (referenced by `broker_orders`) and the configuration needed to reactivate.
- Manual `reconcile` with open-order mode follows the same unfilled rule.
- The Debugging page has a "Reconcile open trades from previous days" button that runs this same close logic only for `bracket_monitor` rows whose `last_occurred_at` is before the current journal day. This lets you clean up historical stale rows without touching today's legitimate open positions.
- `POST /app/debugging/ct-sweep-now` (admin session + CSRF) runs one sweep pass on demand — order probes + flat-close sync + closed-row upgrade. Timing knobs: `CT_SWEEP_INTERVAL_MS`, `CT_VERIFY_DELAY_MS`, `CT_PROBE_GRACE_MS` env vars (prod defaults 60s/12s/120s unchanged). The periodic sweep auto-runs only when `NODE_ENV=production` — dev/test must trigger passes manually (`CT_SWEEP_ENABLED=1` force-enables the interval). The Journal "Open Orders" header shows a dev-only "CT sweep" button (admin + `devMode` session flag).
- CT sweep rate-limit discipline: CrossTrade budgets REST reads per user key (~3 rps/180 rpm, burst 20). All `/v1/api` reads serialize through a shared per-credential limiter (`CT_API_MIN_INTERVAL_MS`, default 350 ms) and a 429 parks that key for the server-supplied `Retry-After`/`retryAfter` cooldown. The sweep fetches each account's orders list once per pass and resolves every open row from it (a direct `/orders/:id` probe only runs for ids missing from the list); `acknowledged` rows are only probed inside `CT_VERIFY_WINDOW_MS` and never after `ct-verified`. Failed book reads back that account off exponentially up to 5 min (a forced `ct-sweep-now` bypasses the cooldown) and are never evidence of absence.
- The Debugging page also has a "Flatten submitted instruments" button (`POST /app/debugging/flatten-submitted-instruments`, admin session). It runs the same cancel/exit + bookkeeping reconcile as `POST /app/exit-all-safeguard` for every account with an enabled TradersPost destination, but only on instrument roots that already have submitted state (open brackets, deliveries that reached or may have reached TradersPost — suppressed/unrouted/failed-to-configure deliveries don't count, unfinished reapply ops, pending/acknowledged/uncertain broker orders — scanned via `listOpenBrokerOrdersByAccount`, unbounded, `pending_traderspost` and `extension_draft_created_and_pending_traderspost` deliveries) — no blanket MNQ/MGC roots. Every account with a disabled destination is reported as skipped, not reconciled. The shared send + reconcile core is `runCancelAllSafeguard` in `src/server.ts`, which serializes through the same per-account `reapply.queue` as proxy entries and reapply work, requires body-level `success` (not just HTTP 2xx), and reconciles local bookkeeping through the destination ticker mapping. The "Clear reapply operations" control only clears incomplete operations and requires broker reconciliation confirmation; `POST /app/debugging/clear-broker-orders` (endpoint only — no UI button) is destructive bookkeeping cleanup: it closes open rows (`cancelled`/`closed`) then hard-deletes all `cancelled`/`closed`/`rejected` ledger rows. `filled` rows survive the purge because they are the dispatch evidence for live positions. It must NOT retire armed `bracket_monitor` rows — clearing our dispatch record proves nothing about the broker, and a healthy working order would otherwise lose its Open Orders row; arms retire only via Pine lifecycle, EOD/reconcile, or per-row operator reconcile where real broker state is asserted. Per-row reconcile in "Order attempts and local state" offers `mark…` on unresolved rows, `retire arm` on terminal `rejected`/`cancelled` entry rows, and `clear` (hard-deletes the ledger row) on `rejected`/`cancelled`/`closed` rows. `retire arm` exists because dispatch-time rejections (e.g. `InvalidPrice: outside price limits`) mark the row terminal without touching the armed monitor row, and the email-rejection path skips rows that are no longer open. Dismissal is refused for unresolved dispatches and `filled` rows — the latter are dispatch evidence for live positions.

## Cancellation Model and ULTRA Lifecycle

- `docs/lifecycle-decisions.md` is the decision-point reference for this whole flow — update it whenever a rule in this section changes.
- TradersPost cancellation is instrument-scoped. The Bridge cannot independently cancel a trade, range arm, bracket, or protective order by supplying its ID. Identifiers are bookkeeping metadata, not broker targeting controls.
- Reapply exists because cancelling the instrument's working orders also removes other ranges' pending orders: rebuild the wanted pending entries after cleanup. Never introduce opposing-arm cancellation on `entry_filled`.
- ULTRA 5.3 emits `entry_armed`, `entry_filled`, `trade_closed`, and `entry_cancelled` lifecycle alerts. `trade_closed` reports `extras.exitReason` equal to `take_profit`, `stop_loss`, or `protected_stop`. `entry_cancelled` reports `extras.cancelReason` equal to `opposite_suppressed_after_tp` or `range_entry_capacity_reached`. These are simulated lifecycle observations, not broker execution acknowledgements.
- `entry_filled` updates bookkeeping only. ULTRA 5.3 emits Pine-owned `entry_cancelled` events when the opposite bracket arm is explicitly retired (TP suppression or range capacity exhausted), so the bridge can keep `bracket_monitor` in sync without inferring intent from `trade_closed`.
- With `reapplyOnTradeCloseEnabled` off, `trade_closed` only records lifecycle history. With it on, the current sequence is instrument-wide cancel, then an unconditional safeguard exit, then re-arm the remaining ranges, nearest the close price first. The safeguard exit is sent whenever reapply plans (i.e., no `filled` bracket exists on the account/instrument), even if the closing trade itself never reported `entry_filled`.
- Re-arms replay the original entry price, which may be stale by the time a close triggers them. A `stop` re-arm whose level is already through the close price (buy stop at or below it, sell stop at or above it) would be rejected by the broker, so the step is planned as `skipped` — no dispatch, no replacement armed row, and the cancel sweep still retires the arm's original monitor row. The operator gets a warning toast listing the skipped arms.
- Reapply requires an enabled account destination, enabled route, and `reapplyOnTradeCloseEnabled`. The route's `runScheduled` days gate admission of *new* work: an `entry_armed` on an unscheduled day is not journaled and no bracket is admitted. Lifecycle events for a bracket that already has a `bracket_monitor` row still resolve it regardless of schedule — `listLifecycleBracketAccounts` adds the accounts holding matching monitor rows (including reapply-alias replacements) as recipients — and, because `routeEnabled(route, cleanup)` bypasses only the day check (not enabled/deprecated/review checks), a close on an unscheduled day still runs the cancel/exit/re-arm cleanup. A route whose `traderspostEnabled` is off resolves the monitor locally with no broker dispatch. It uses the destination instrument after ticker normalization and account mapping, so NQ and MNQ share a guard when both route to MNQ.
- If any monitor bracket is filled on the account/destination instrument, a new close's reapply is skipped. The guard is checked again before outbound steps; a fill during an existing operation pauses it. Cleanup still runs when there are no other armed brackets. A `filled` monitor only counts when an entry order was actually dispatched for it (`broker_orders` row whose `dispatch_status`, falling back to `status`, is non-`rejected` — a rejected send stays evidence-free even if lifecycle later flips `status`) — Pine fills are simulated, so a bracket whose send never ran (wedged queue, suppressed/disabled route) holds nothing at the broker and does not block cleanup.
- The guard uses Pine-derived bookkeeping, not live broker reconciliation. An undelivered/late Pine fill or broker-only position cannot be detected by this guard.

## Broker Orders and Reapply

- `src/reapply.ts` coordinates the reapply flow, but its records now live in `broker_orders` rather than in `bracket_monitor` or `trade_events`.
- `broker_orders` has one row per outbound dispatch (TradersPost or CrossTrade). `forwardToTradersPost` upserts the row from the prepared outbound payload (post destination transforms), so `instrument`, `quantity`, and prices reflect what the endpoint actually receives — e.g. the 10x micro quantity under `micros_only`. The cancel-all safeguard ledgers its `exit` dispatches with `bridge-safeguard-<uuid>` order ids. It tracks `bracket_id` (Pine logical bracket), `order_id` (unique outbound order id, e.g. `bridge-reapply-<uuid>`), `action` (`buy`/`sell`/`cancel`/`exit`), `status` (`pending`, `acknowledged`, `rejected`, `uncertain`, `filled`, `closed`), `destination` (`traderspost`/`crosstrade`; legacy rows predate the column and read as `traderspost`), `quantity`, `price` or `stop_price`, `proxy_alert_id`, `proxy_delivery_id`, `occurred_at`, and `error_text`.
- `bracket_monitor` rows exist for both the Pine `bracket_id` and each delivered replacement. Reapply updates the Pine bracket to `cancelled` operationally, records a `broker_orders` cancel row, and — once the re-arm entry is delivered — creates a monitor-only `armed` `bracket_monitor` row for the replacement bracket so the rearmed range stays visible in Open Orders. No `trade_events`/`range_trade_events` rows are written for replacements.
- `bracket_reapply_aliases` maps a Pine `bracket_id` to the current active `broker_orders.order_id` (which is also the replacement's `bracket_monitor.bracket_id`). When a later Pine `entry_filled`, `entry_cancelled`, or `trade_closed` arrives, `recordBracketMonitorEvent` uses this alias to redirect the write to the replacement's monitor row and update the linked `broker_orders` row. If a Pine fill/close arrives while the re-arm request is still in flight, the original row resolves first and no replacement armed row is created (the alias still binds, so subsequent events keep targeting the original row).
- The same lifecycle events also transition the *ordinary* (non-alias) entry dispatch row via `updateOpenEntryBrokerOrderStatus` (`status_source='lifecycle'`), matching on `bracket_id` + side-derived action (`buy` for long, `sell` for short; a `NULL` side also matches, so entry payloads that omit `bracketSide` still resolve), which excludes precise-TP/cleanup dispatches for the same bracket. `entry_filled` → `filled`, `entry_cancelled` → `cancelled`, `trade_closed`/`exit_filled` → `closed`. Mirroring the monitor model, a `filled` order can close but cannot be cancelled. Only the newest matching open attempt transitions, so a later lifecycle event does not silently resolve a still-uncertain earlier resend.
- Internal force-retire paths keep the ledger in step too: `retireReapplyArm` (reapply retirement) and `retireBracketMonitorEntry` (EOD/reconcile/safeguard bookkeeping) call the same entry-order transition, so a bracket retired without a Pine lifecycle event doesn't leave a stale `acknowledged` working order.
- The sequence is cancel, then an unconditional safeguard exit, then re-arm. Flatten legs (`cancel`/`exit`) are always attempted — a failed or uncertain cancel does not skip the exit that flattens a possibly-live position. A failed or uncertain flatten leg pauses the operation before any re-arm (fresh orders are never placed over unresolved cleanup); a failed re-arm halts the remaining entries. There is no automatic 120-second backoff/retry loop.
- A newer `trade_closed` on the same account+instrument supersedes an unfinished reapply op: the stale op is completed with its ledger preserved (never-sent steps become `skipped`, their queued deliveries `suppressed_reapply`), and a fresh op plans against the current armed brackets — including arms the stale op retired for its own cancel sweep but Pine never resolved (carried forward so their ranges are not silently dropped). Arms whose logical trade already has an armed replacement are not carried.
- `bridge-reapply-<uuid>` values continue to be used as the outbound `order_id` for re-arm dispatches, but they are not `tradeId`s and do not appear in `trade_events`.
- Repeated reapply for the same bracket appends new `broker_orders` rows instead of multiplying `trade_events` rows. Each `broker_orders` row has its own UUID and its own `proxy_delivery_id`.
- Every outbound resend gets a fresh ledger row: admin delivery retries use `bridge-<deliveryId>-r<n>` order ids (one per prior attempt) so a retry never overwrites the prior attempt's status/error history. The precise take-profit retry path does the same. Reapply resends use `<step.brokerOrderId>-r<n>` — the stable `brokerOrderId` stays the logical identity (alias target and the replacement monitor row's `bracket_id`) while each actual dispatch is a separate auditable row; status writes resolve the newest attempt via `latestBrokerOrderAttempt`.
- Transport failures (`fetch` rejection with a `cause` — socket close, refused, DNS/TLS) get ONE automatic retry after 750 ms in both the proxy dispatch path and the safeguard/flatten path. Timeouts/aborts are never retried (the request may already be in flight), and neither are response-body read failures (the POST was already accepted). The failed attempt's `broker_orders` row is marked `uncertain` and the retry dispatches under a fresh `-r<n>` order id, so both sends are auditable. The retry sleep is abortable — a watchdog release during the delay cancels the retry before it fires.
- A queued send re-reads the delivery row at dispatch time inside the account queue: a delivery whose status no longer expects a send (e.g. retired to `suppressed_safeguard` by a flatten that ran first) is never dispatched.
- Operator-initiated resends (`/app/api/journal/resend-delivery`, `/admin/proxy-deliveries/:id/retry`) are NOT blocked by an unresolved prior attempt: the operator takes responsibility for the duplicate-order risk if the earlier request secretly reached TradersPost. The resend dialog warns about this. Route/destination enablement is still re-checked at dispatch time.
- `POST /app/debugging/reconcile-broker-order` (admin session) marks an unresolved `broker_orders` row (`pending`/`uncertain`/`acknowledged`) to an operator-verified status (`acknowledged`/`filled`/`closed`/`rejected`/`cancelled`, optional `note` into `error_text`). Bookkeeping only — no broker traffic. Marking an entry order `rejected`/`cancelled` retires its armed monitor row unless another open dispatch covers the arm (shared `retireUncoveredArmedMonitorRows` helper, same rule as the failure-email path). The Broker orders card shows a per-row "mark…" control on unresolved rows.
- EOD, news-flatten, reconcile, and admin cleanup are the only operations allowed to write synthetic `trade_events` (`entry_cancelled` and `trade_closed`) when forcibly closing an unfilled bracket. Reapply does not write `trade_events`.
- Proxy deliveries and reapply operations share a per-account operation queue; network calls retain the 250 ms minimum interval. Unfinished operations do NOT block new entries — entries always dispatch to stay aligned with Ultra alerts; per-account serialization already prevents mid-op interleaving, and a bracket armed just before an op runs is picked up by that op's re-arm pool. External cancel/exit deliveries invalidate the unfinished plan.
- Queue tasks have a 60 s watchdog (`TradersPostRateLimiter` second ctor arg; per-call third arg overrides for batch work — safeguard flattens and reapply `execute` runs use 10 minutes): a task that never settles aborts its `AbortSignal`, releases the queue, and rejects its caller rather than wedging the account forever. Tasks that loop over sends must check `signal.aborted` between iterations, and `forwardToTradersPost` receives it via `context.taskSignal` so a released task bails instead of mutating alongside the next dispatch; an aborted flatten skips reconciliation and returns partial results. Two ledger obligations still outlive a released task: a released entry persists its precise take-profit intent and a pending (resendable) TP delivery — the entry may already be live without recorded protection — without dispatching the TP, and a safeguard send released by the outer queue watchdog records its pending `broker_orders` row `uncertain` instead of orphaning it. TradersPost fetches additionally race a hard timeout (`traderspostHardTimeoutMs`, default 20 s) on top of the 10 s `AbortController`, because abort does not always settle a stuck undici request. A dispatch failure inside the alert fan-out marks that delivery failed, ledgers a `proxy_delivery_attempts` row (so resends allocate `-r<n>` order ids rather than upserting over the interrupted attempt's `broker_orders` row), and continues to the remaining accounts instead of aborting their deliveries. The safeguard/EOD `sendOne` path uses the same hard timeout and isolates failures per instrument so one hung fetch cannot abort the rest of a flatten.
- On startup (`reapply.recover()`), leftover `pending_traderspost` / `extension_draft_created_and_pending_traderspost` deliveries are swept to their `*_failed` variants and `pending` `broker_orders` to `uncertain` — a restarted process cannot have an in-flight dispatch, so pending rows are orphaned evidence. Each swept delivery gets a `proxy_delivery_attempts` row so a later resend allocates a fresh `-r<n>` order id. Recovery runs in the background (`src/index.ts` does not await it before listening); a failure is logged as a `startupRecoveryFailed` fatal event rather than aborting boot, and per-operation failures are caught so a stuck task leaves the operation incomplete for operator retry.
- HTTP 2xx with an explicit `success:true` body means webhook delivery, not confirmed broker fill/cancellation. A 2xx without `success:true` (missing, malformed, or false) is never treated as delivered: `success:false` and definite 4xx map to `rejected`, everything else to `uncertain`. Cancel-before-exit can leave a still-open broker position without protective orders until exit executes; pauses require operator attention.
- The `proxy_alert_id` on `trade_events` refers to the *lifecycle* `buy`/`sell` `proxy_alert`. `broker_orders` stores the *dispatch* `proxy_alert_id` and `proxy_delivery_id` from `proxy_deliveries`. Delivery status lookup should join `broker_orders` on `proxy_delivery_id` or `proxy_alert.source_reference`, not on `trade_events.proxy_alert_id`.

## TradersPost Reapply Payload Shapes

- Instrument cancel:
  - `action: 'cancel'`
  - No `bracketId`, `bracketSide`, or `tradeId`
  - `extras: { rangeName, lifecycleCancel: 'trade_closed', reapplyOnTradeClose: true, reason: 'reapply_cancel' }`
- Safeguard exit:
  - `action: 'exit'`, `orderType: 'market'`
  - No `bracketId`, `bracketSide`, `tradeId`, `quantity`, or `quantityType`
  - `extras: { rangeName, lifecycleExit: 'trade_closed', reapplyOnTradeClose: true }`
- Re-arm:
  - Original `buy`/`sell` shape with a fresh `bracketId` and `tradeId`
  - `extras` retains `rangeName`, adds `source: 'reapply'`, `originalBracketId`, and `reapplyOnTradeClose: true`

## Recovery and Known Limitations

- A newly accepted close and its per-account reapply obligations are recorded in one SQLite transaction. `reapply_operations` stores the plan, stable replacement identities, step delivery IDs, and completion status. Step alert/delivery creation is transactional.
- `src/index.ts` starts unfinished reapply recovery in the background in non-test mode — boot must not wedge on a crashed or slow op. Recovery resumes incomplete operations one at a time through the same per-account queue, so a live entry waits behind at most the one in-flight recovery op (bounded by that op's watchdog); priority-queueing an entry ahead of an in-flight reapply cancel would be unsafe. Tests call `app.locals.recoverReapplyOperations()` explicitly. Completed operations and already-successful deliveries are not sent again; duplicate closes can resume their existing incomplete operation.
- Unsent steps and definite HTTP client rejections can resume. An interrupted in-flight request, timeout, server error, or missing protection confirmation is treated conservatively as uncertain and requires reconciliation, not blind replay.
- Recovery pauses if destination settings changed, the route is disabled, another bracket is filled, an external cleanup invalidated the plan, or the operation is older than 15 minutes. The operation's own remaining steps stay unsent until it is completed or explicitly abandoned — new alert entries are never blocked by it.
- This recovery covers operations created by the new coordinator. It does not bulk-replay historical closes, arbitrary pending proxy deliveries, or orphan incoming alerts. There is no automatic opposing-arm cancellation on startup.
- Admin-key API: `GET /admin/reapply-operations` lists incomplete operations; `POST /admin/reapply-operations/:id/retry` resumes only safe steps. Generic individual-delivery retries cannot bypass the coordinator.
- After manually reconciling broker positions and cancelling unwanted working orders, `POST /admin/reapply-operations/:id/abandon` with `{ "brokerReconciled": true }` retires the captured pending pool and closes the operation without sending broker requests. This is operator confirmation, not an automated broker check. Pauses are also retained in Bridge logs and emitted as persistent error toasts.
- The Open Orders cards surface the underlying `entry_armed` TradersPost delivery status (`entryArmedDelivered`) so a `filled` row with a red X means Pine reported a fill but the original entry order was never delivered to the broker. This can happen when `traderspostAccountEnabled` is off or the TradersPost delivery fails for one account while other accounts in the same range are filled.
- Pine range rollover still clears simulated state without broker cleanup. BE rearm is exposed but not wired; pre-arm candle extremes can be reused by the fill logic. Pine tick behavior requires TradingView paper validation, not just server tests.
- Documentation describes implementation, not authorization to send real orders. Tests must use isolated databases and mocked outbound requests.

## 24h P&L Review

- `GET /app/api/accounts/:accountId/pnl-review` returns a bounded window: `since`/`until` are inclusive on both ends (`occurred_at >= since AND occurred_at <= until`), so future-dated `trade_closed` events never appear.
- `trades` returns the *entire* window (not capped) — the summary, per-range aggregates, equity curve, and best/worst cards must all agree. The client's trade table renders only the first 200 rows (`TABLE_DISPLAY_LIMIT` in `AccountPnlReview.tsx`) and shows a truncation note.
- Range P&L aggregates are keyed by `(rangeName, instrument)` — identical range names on different instruments stay separate.
- `excludedFromPerformance` trades are excluded from summary, ranges, best/worst, and the equity curve but remain in the table.

## CrossTrade Dispatch

- Accounts can optionally configure a CrossTrade destination (`crossTradeWebhookUrl`, `crossTradeSecretKey`, `crossTradeAccountName` on the account config). When both the webhook URL and secret key are set, `forwardToTradersPost` converts the internal TradersPost-shaped payload with `toCrossTradeMessage` (`src/crosstrade.ts`) and POSTs it to the CrossTrade webhook instead of TradersPost.
- The integration is NT8-only: the wire `destination` is always `'nt8'` (CrossTrade NT8 Add-On — NinjaTrader 8 must be running with the add-on connected), and `account` is the NinjaTrader account name (e.g. `Sim101`).
- The command mapping is `buy`/`sell` → `command: 'place'` (order types `market`/`limit`/`stopmarket`/`stoplimit`/`trailingstop`), `cancel` → `cancelorders`, `exit` → `flatten`, all instrument-scoped with the secret in the `key` body field. Record-keeping extras ride in `notes` (`src:`, `bracket:`, plus scalar extras); `order_id` carries the bracket id.
- Range configurations carry the breakeven and pairing policy: `breakEvenEnabled` (yes/no), `breakEvenTriggerTicksCents` (how far price must run to arm the BE move), `breakEvenOffsetTicksCents` (where the stop lands past entry), and `ocoMode` (`'oco'` default — the two arms pair via native `oco_id`; `'both'` — both sides may be live, no `oco_id` sent). ATM strategy attach is opt-in, not default: the dispatch site (`forwardToTradersPost`) injects `extras.appendAtm=true` only for entries whose range has `breakEvenEnabled` — those entries name `atm_strategy` after the range, and a missing NT8 template rejects the place, which is intentional: a breakeven range without its template must fail rather than run unprotected. `ocoMode: 'both'` injects `extras.oco=false` at the same site. `extras.atmStrategy` overrides the template name and itself implies opt-in; `extras.appendAtm=false`/`extras.ocoId`/`extras.oco` per-alert values always win over injected policy. The debugging test card's "ATM strategy name" field overrides the default.
- Entries also carry `oco_id` so a range's two arms form a native NT8 OCO pair — when one entry fills, NinjaTrader cancels the other at the broker without depending on our `cancelorders` dispatch. NT8 permanently burns an oco_id once its group resolves, so the key derives from the bracket id with the `-long`/`-short` token removed (ULTRA arm pairs share one stem, unique per arming event — e.g. `ultra-v5.3-MNQ1!-<ms>-<seq>-long-arm-18` → `ultra-v5.3-MNQ1!-<ms>-<seq>-arm-18`). A bracket id with no side token maps to itself (unpaired — safe degrade). `extras.ocoId` overrides the key, `extras.oco=false` opts out. The debugging card's "OCO group id" field is an optional override; leave it empty and each test run gets a fresh `debug-<runId>` group automatically.
- **CT leg attribution (protection vs arm)**: a filled position's *protection legs* are the SL/TP exit orders attached to it; an *opposite-side arm* is a still-armed ENTRY on the other side of the range — both live in the same book and both are `ownerStrategy`-marked when a strategy owns them, so they must not be conflated. Missing-protection detection (`crossTradeAtmMissing`) attributes legs to a filled entry by the ENTRY's `ownerStrategy` (NT8 marks strategy-spawned orders with the instance name — `'THE MAX WIN - 1'` — not the range name; for BE ranges the owner IS the range name because `atm_strategy` is sent). Ownerless legs on a strategy-owned entry are plausible by quantity + submission-time only (same-owner rows reaching that branch are the arm, already excluded). Ownerless entries need config SL/TP price-matching — the only discriminator vs an opposite-side arm or manual order. Missing = no attributable leg → warn for every range, BE or not. The `crossTradeOrphanOrders` check skips Working OPPOSITE-action OCO pairs (`ocoId` shared, both `Working` — an armed arm pair is not an orphan; a real orphan's partner is gone). `crossTradeLegSignature` bridge_logs dump each filled entry's verbatim sibling rows once per 46h to validate these rules against real NT8 data.

- `broker_orders` still ledgers the normalized internal payload (ticker/action/qty/prices), not the CrossTrade wire format. Responses still require an explicit `success: true` body; `failureMessage`/`error` fields are surfaced.
- Reapply is suppressed for CrossTrade-configured accounts (`reapply.ts` skips planning when `crossTradeWebhookUrl` is set); EOD blanket sweeps and the safeguard flatten still dispatch through the same converted path.
- The Debugging page has a "CrossTrade API test" card (`POST /app/debugging/crosstrade-test`, admin session) that runs a payload through `toCrossTradeMessage` and posts it, returning the exact sent message and raw response.
- CrossTrade also has a REST API (`/v1/api`, Bearer auth) for live NT8 reads — separate from webhook sends. CrossTrade issues a single Secret Key that doubles as the Bearer token, so reads authenticate with `crossTradeSecretKey` — no separate credential is configured. `src/crosstrade.ts` derives the API base from the webhook URL origin (`/v1/send/...` → `/v1/api`) and exposes `fetchCrossTradeOrders`/`fetchCrossTradePositions`/`fetchCrossTradeOrder`. Single-order lookup accepts our caller-supplied `order_id` (the bracket id) — CrossTrade resolves it from the order's UserData.
- `GET /app/debugging/crosstrade-state?accountId=` returns NT8-reported working orders and positions next to local bookkeeping (unresolved CT `broker_orders` + active `bracket_monitor` rows) for eyeball reconciliation — it never mutates local state. The same response carries an ATM preflight: `atmTemplates` (everything NT8 reports via `GET /v1/api/atm-templates`) plus `atmPreflight.required`/`missing` — the BE-enabled ranges routed to that account whose named templates are absent on NT8. Templates are NT8-install-wide, not per-account; there is no create API, so missing ones must be built in the NT8 UI (or dropped into `Documents\NinjaTrader 8\templates\AtmStrategy\` as XML). `GET /app/debugging/crosstrade-order?accountId=&orderId=` probes one order; it always returns 200 with an `ok` flag because a failed lookup is itself the answer. Both require the session to own the account (admins can read any), and surface unconfigured accounts as 409. The Debugging "CrossTrade broker state" card drives both.
- CT broker evidence resolution (`resolveCrossTradeBrokerOrder` in `src/server.ts`) probes NT8 for unresolved CT entry rows and applies definite answers to the ledger: `Working` → `acknowledged`, `Filled` → `filled`, `Cancelled`/`Rejected` → terminal + armed-monitor retirement via `retireUncoveredArmedMonitorRows`, confirmed not-found → `rejected` only once the 2-minute dispatch grace window has passed (younger rows report `in_flight`, untouched). Failed reads and unrecognized NT8 states are `unknown` — never evidence of absence. The probe keys on `bracket_id` (the wire `order_id`), not the ledger row id. Only entry actions are probed — cancel/exit are commands with no order to find. Two drivers use it: a 60 s background sweep (`sweepUncertainCrossTradeOrders`, logs `crossTradeSweepProbe`) covering every CT row pending/uncertain past grace, and the admin `POST /app/debugging/reconcile-crosstrade` (the card's "Reconcile local rows" button), which probes all unresolved CT entry rows on an account on demand. Every applied outcome writes a `crosstrade` bridge log; the sweep additionally emits SSE toasts — `toast:success` on confirmed Working/Filled/Cancelled (a cancel is routine lifecycle — usually OCO sibling fill), persistent `toast:warning` only on `rejected` — while `unknown`/`in_flight` stay silent and retry next tick. TradersPost uncertainty semantics are unchanged. Pine lifecycle remains authoritative for the *event stream* (entries, cancels), but for `trade_closed` realization on CT accounts, matched broker fill data is authoritative over Pine's report — see the flat-position close synthesis bullet below.

- **Absence is never evidence against a confirmed order.** In both the per-order probe and the post-burst whole-book verify (`verifyCrossTradeAccountBook`), an order NT8 previously confirmed (`status='acknowledged'`) cannot be downgraded to `rejected` because it is absent from a list snapshot — NT8 retains terminal orders in the book, so real terminal states are found positively. Absence still rejects `pending`/`uncertain` rows past the 2-minute grace within the 30-minute verify window.
- **The 60 s sweep covers `acknowledged` rows too** — open entries are re-probed until they resolve terminal (`listUnresolvedCrossTradeOrdersBefore` no longer exempts `ct-verified` acknowledged rows). Nothing is "verified once, never checked again."
- **Flat-position close synthesis** (`syncFilledBracketClosures`, runs in the same sweep): a `filled` monitor row whose instrument is flat at NT8 and has no working orders remaining gets a synthesized `trade_closed` written to BOTH `trade_events` and `range_trade_events` (event id `ct-flat-<bracket>-<side>-trade_closed`, `adjustment_note` records the basis). Realized ticks are computed from the NT8 entry fill vs the opposite-action `ownerStrategy`-owned exit fills (`averageFillPrice`/`inferredTickSize`/`inferredTickDollars`); `ownerStrategy` attribution excludes the user's manual orders on the same instrument. Unmatched exits close at breakeven with a note. A `toast:success` announces the close. **Journal precedence: matched broker data wins over Pine, in both directions** — `trade_closed` dedupes by tradeId, not eventId, at both tables. A ct-flat row with a matched exit (`exit_price` set) is authoritative — Pine's later `trade_closed` is skipped; and when Pine closed first, a matched ct-flat REPLACES the row's realization in place (fill prices carry real spread/slippage). Unmatched ct-flat rows (null exit) never overwrite — Pine's numbers upgrade them. The monitor still closes on flat-book evidence either way.
- **Close synthesis requires broker-confirmed entry evidence**: a present-but-unfilled NT8 entry row defers the close (`crossTradeCloseDeferred` log, once per bracket). An absent entry row falls back to prior broker-confirmed ledger state (`dispatch_status` acknowledged/filled via ct-verified/probe/operator — Pine 'lifecycle' fills alone do NOT qualify; `hasBrokerConfirmedEntryOrder`). This prevents Pine-only 'filled' monitors from fabricating a position close.
- **Shared-instrument ambiguity closes, doesn't hang**: two `filled` brackets on one instrument root can't share exit-fill attribution — the rows still close (flat book is proof) as unmatched breakeven with `crossTradeAttributionAmbiguous` logged; a later Pine close upgrades the realization.
- **Pine-first upgrade pass**: monitor rows Pine already closed (`state='closed'`, non-ct-flat, within the 30-min window) are re-examined each sweep — when the book attributes the entry fill + a strategy-owned exit fill (ownerStrategy = range name, postdating the entry), the journaled realization is REPLACED in place (`crossTradeBrokerRealizationUpgrade` log). Accounts hosting such rows join the sweep candidate set (`listAccountsWithRecentlyClosedMonitorRows`), so the pass runs even when nothing else is pending.
- **NT8 burns resolved OCO ids forever** — a re-armed bracket (Ultra reuses the bracket id after a terminal close) would be rejected by NT8 for reusing its `oco_id`. CT entry dispatches therefore carry an attempt suffix on the wire: `order_id`/`oco_id` go out as `<bracketId>-aN` where N = prior potentially-reached dispatches for that arm (any delivery not suppressed/failed, excluding the in-flight one — count includes uncertain/pending because a redundant suffix is harmless, a reused id is not). Both arms of a pair count symmetrically, so they suffix identically and OCO grouping is preserved. `broker_orders.order_id` stores the wire id (probes look it up there); `bracket_id` keeps the logical Ultra id. `matchesCtOrderId` strips `-aN` when correlating.
- **Re-armed brackets re-open**: a terminal (`closed`/`cancelled`) monitor row accepts a NEWER `entry_armed` (occurredAt > last) as a fresh attempt — Ultra reuses bracket ids after close; replayed historical arm events carry stale timestamps and stay ignored.
- **ATM divergence warning**: after a book verify, for BE-enabled (ATM-managed) entries that filled, the strategy's live legs (`Stop*`/`Target*` rows, `ownerStrategy` set) are compared against the range's configured SL/TP ticks — divergence >1 tick emits a persistent warning toast once per bracket plus a `crossTradeAtmMismatch` log. CrossTrade cannot read template contents (`GET /v1/api/atm-templates` lists names only), so the live legs are the observable truth. `GET /app/api/ranges/:name/atm-template` renders the NT8 template XML fresh from the current DB config on every request — re-download + re-import after changing settings.

## Webhook Tuning

- `PROXY_ASYNC=1` makes `/proxy/:secret` return `202` immediately and process the payload in the background. This avoids TradingView timeouts under load but removes the per-delivery response from the webhook body. If reapply or delivery behavior looks off after enabling this, review `bridge_logs` and `proxy_deliveries` closely before keeping it on.

## Suppressed Deliveries and the Blocked Badge

- The Open Orders "Blocked" badge derives an arm's `entryArmedDeliveryStatus` from the deliveries of alerts sharing its bracket. Attribution picks the **strongest evidence, then recency** — `delivered` ranks first, then `failed`, then `extension`, then `suppressed_*`, then no delivery — so a duplicate re-send suppressed as `suppressed_duplicate` can never mask the original delivered send. `blocked` only displays when a suppressed status is genuinely the best evidence (the entry never sent).

- `routing_disabled` now means only "routing was off" — route/destination disabled, or disabled while queued. Guard refusals use distinct `proxy_deliveries.status` values:
  - `suppressed_duplicate`: the bracket's monitor row is still live (`armed`/`filled`) — a repeat of an in-flight entry is refused. Terminal rows allow re-dispatch (see re-armed brackets above).
  - `suppressed_reapply`: historical only — an unfinished reapply operation used to block new entries on that instrument. Entries now always dispatch; the status remains on existing rows.
  - `suppressed_guard`: safety guards (unrelated open position/order, TP protection invariant, stale reapply arm, missing source entry, opposite-entry cancel guard).
  - `suppressed_safeguard`: a `pending_traderspost` or `extension_draft_created_and_pending_traderspost` delivery retired by the cancel-all safeguard.
- Preflights return `{ allowed: false, reason, status? }`; the delivery records `preflight.status ?? 'suppressed_guard'`.
- Lifecycle events still record `bracket_monitor` state even when the entry order was suppressed — ULTRA's view of the arm is preserved. `bracket_monitor.delivery_suppressed` is set to 1 at `entry_armed`/`entry_filled` time when `latestEntryDeliveryStatusForBracket` reports a `suppressed_*` status, and merges on update so a later fill can mark it.
- Open Orders maps `suppressed_*` to `entryArmedDeliveryStatus: 'blocked'` with `entryArmedDeliveryDetail` carrying the raw status; the client renders a "Blocked" badge. `routing_disabled` still maps to `unknown` (no badge).

## Email Ingest

- `POST /email/:secret` ingests inbound email and requires the dedicated `EMAIL_INGEST_SECRET` — it deliberately does not fall back to `PROXY_WEBHOOK_SECRET`, since that secret is embedded in every TradingView webhook URL and must not authorize a `broker_orders` mutation path. Unset means every request is `401`.
- The secret is the only gate: every email that normalizes is stored as an `email` bridge log for review, regardless of sender or content. `senderTrusted` records whether the sender was `@traderspost.io`; `notFailure` marks mail that isn't a failure report. Forwarded failure emails (e.g. for testing) are processed normally.
- Only failure mail attempts ledger mutation. Correlation is strict: an echoed `bracketId` (normalized like stored ids) matches only that bracket, and the echoed `action` scopes the match so a TP leg with the same bracket but the opposite action is not falsely rejected. Without a bracketId, only a *unique* recent same-instrument candidate is auto-resolved; multiple candidates are logged as `ambiguous` for operator review with nothing mutated.
- A resolved rejection also retires the matching `armed` `bracket_monitor` row to `cancelled` (last_event_id `email-reject-<orderId>`) when the rejected order is that arm's entry action — a rejected TP/exit leg does not void a working entry, and the arm survives while another open dispatch still covers it. This keeps Open Orders from showing a working order the broker no longer has. `listOpenTradeSanity` also exposes the latest `broker_orders` status/error (`brokerOrderStatus`, `brokerOrderErrorText`) so a webhook-accepted-but-broker-rejected order is flagged even when `deliveryStatus` is `traderspost_delivered`.
